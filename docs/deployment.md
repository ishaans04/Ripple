# Deploying Ripple

**Recommended first production host: Railway Pro, with one always-on Ripple Docker service and a private PostgreSQL service in the same region.** This matches the implemented topology and checked-in `railway.json`. Keep the worker in the application process; no GPU, inference API, Redis, separate frontend host or Kubernetes cluster is required. Camera inference runs in the viewer's browser.

This recommendation concerns operational fit. Local/CI capacity measurements are not a hosted capacity guarantee. Run the same workload on an isolated staging installation before enrolling real channels. Start with room for roughly 2 application vCPUs / 2 GB RAM and 2 database vCPUs / 2 GB RAM; these are starting resource limits, not a claim that every workload uses or fits them. Adjust from the recorded CPU, RSS, database I/O, backlog and latency evidence. Storage must include retained accepted history and receipt hashes; raw-input retention does not cap total season history.

Railway supports [WebSockets over HTTP/1.1](https://docs.railway.com/networking/public-networking/specs-and-limits). Its [deployment health check](https://docs.railway.com/deployments/healthchecks) protects rollout; use a separate continuous uptime monitor. Leave **Serverless/App Sleep disabled**: callbacks, persistent sockets and durable round deadlines require an available process. Start with one replica and one database region; the database runtime lease and sorted locks protect ordered processing during restarts. Horizontal/multi-region scaling requires a measured rollout rather than changing replica count to conceal a backlog.

For an India/APAC pilot, choose Singapore; for predominantly US broadcasters, choose the closest US region. Keep both services together. The [current regions](https://docs.railway.com/deployments/regions) include Singapore, California, Virginia and Amsterdam. Audience/provider latency matters more than the developer's location alone.

## Setup

1. Create a Railway project and a persistent PostgreSQL service. Use PostgreSQL 18, a private connection and a durable volume. Keep the database off the public internet except a restricted, temporary operator connection when necessary. Ripple defaults to 48 pooled connections, configurable from 8 to 64. Reserve database slots for both old/new application processes during a rolling deployment plus maintenance, migrations and operator access; reduce the pool or configure an appropriate PostgreSQL limit before rollout if that budget does not fit.
2. Connect this GitHub repository as a Dockerfile service, using the repository root. Keep the migration pre-deploy command, start command, `/health/ready` and drain period from `railway.json`. A failed migration or readiness check must block rollout. Do not run the local Compose database credentials in production.
3. Reference the database's private URL as `DATABASE_URL`. Keep `HOST=0.0.0.0`; use Railway's injected `PORT`. The image already sets `WEB_ROOT`. Set `DATABASE_POOL_MAX=48` within the connection budget above, `LOG_LEVEL=info`, and initially `ENABLE_LIVE_TWITCH=false`.
4. Generate a stable HTTPS domain and verify `/`, `/health/ready`, `/sandbox`, `/studio`, `/privacy`, worker/model asset MIME types, and WebSocket upgrades. Run the installed judge journey against staging. Never put access capabilities in a support ticket or screenshot.
5. Follow [Twitch setup](twitch-setup.md) for exact OAuth redirect URLs, two consenting broadcaster accounts, the operator bot and independent secrets. Put real values in provider secret variables, not the repository or a Docker build argument. Keep `ACTOR_HASH_KEY` stable for the installation; a change intentionally refuses startup rather than changing vote identity silently.
6. Enable database backups and PITR explicitly, verify the first backup and WAL archiving, and perform a separate-database restore before enabling live input. Railway's [PostgreSQL backup guide](https://docs.railway.com/guides/postgres-backups-restores) describes dashboard PITR setup and an approximately four-week archive window. Publish the actual provider retention, including snapshots and WAL, in your privacy notice; the local seven-day backup baseline is not the provider's PITR default. Reapply the independent erasure ledger before exposing a restore.
7. Add uptime, callback-latency, worker-lag, failed-input, disk, backup-age and spend alerts. Verify graceful restart, an unavailable database and an expired/revoked grant on staging. Record outcomes, revision, region, resources and observed RPO/RTO. Complete the deferred live Twitch/OBS/studio-to-raid journey before calling the service live-accepted.

## Cost and alternatives

Checked 30 October 2026: [Railway pricing](https://docs.railway.com/pricing) lists Pro at a $20/month minimum usage commitment, RAM at $10/GB/month, CPU at $20/vCPU/month, volume storage at $0.15/GB/month and egress at $0.05/GB. The commitment counts toward usage. A continuously consumed total of 2 vCPUs and 2 GB across both services is about $60/month before storage, traffic, backup archives and taxes; a 4-vCPU/4-GB total is about $120. These are arithmetic examples, not quotes or measured bills. Set a soft spend alert and inspect a week's usage; a hard billing cap takes the app offline when reached.

Render with a paid Docker web service and paid managed PostgreSQL is a reasonable alternative when you prefer that provider's database operations and billing. A VPS can cost less but makes you responsible for patching, TLS, off-host backups, WAL, monitoring and recovery. Static hosting alone, request-only functions and sleeping free services do not fit Ripple's current persistent-worker design. Recheck provider pricing and backup terms before purchasing.

No hosted service or paid resource has been created by Phase 10 implementation. The final live acceptance and production credentials remain with the operator.
