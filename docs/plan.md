# Ripple delivery plan

This plan sequences the [PRD](prd.md) feature register (P01-P40) and the [Cocoon Studio addendum](cocoon-studio.md) into phases. Cocoon Studio turns a streamer's break into a bounded creative task: viewers shape a shell by hand or pointer, chat picks a design with a legal gene trade-off, and the approved design hatches at a safe boundary and travels with raids. The addendum has no requirement identifiers, so this plan assigns S01-S21 (see [Cocoon Studio register](#cocoon-studio-register)); each is a pre-release requirement like a P requirement.

Phases run in order. Phases 0 through 3 are complete. The user has directed implementation to continue with sandbox and synthetic checks while the test Twitch accounts, bot, and public HTTPS URL are unavailable: real integration acceptance stays explicitly pending and never counts as completed live evidence. All other exit checks remain prerequisites for the next phase. The [progress record](progress.md) tracks that deferral and actual evidence. The order follows the PRD's dependency order (section 23), with two changes:

- A synthetic input adapter is built with the event backbone so the game can be developed and demonstrated without live Twitch credentials.
- The studio's pure rules and browser editor come directly after the engine. The addendum (section 30) asks for browser, worker, and hand-tracking model compatibility to be proven, and blueprint rules property-tested, before any studio state goes live; neither depends on a later phase. The rest of the studio follows the systems it reuses: the event backbone, Twitch identity and ballots, raids, the novel mechanics, and the product surfaces.

This is a dependency order, not a calendar estimate. The addendum adds scope; nothing in the PRD is removed to make room for it.

### Decisions to settle in the phase that builds them

Phase 2 settled the following addendum gaps; the decisions and tests are recorded in [delivery progress](progress.md):

- **Keep current:** terminal unchanged outcome, including empty shortlists and no votes; no approval or hatch.
- **Cosmetic-only hatches:** consume the same eligible future mutation slot and preserve genes/fitness.
- **Ties against Keep current:** Keep current wins those ties; finalist-only ties retain seeded order.
- **Founder appearance:** versioned neutral `shell-v1` segmented shell, without studio or artist provenance.

## Not scheduled

The addendum defers these studio expansions (section 5.2); they must not delay the shell-to-raid loop:

- Editors for further anatomy, such as tendrils and travelling membranes
- Coordinated assembly by several simultaneous editors
- Recorded motion signatures using bounded animation curves
- Optional local presence analysis (section 7.5); if built later, it needs separate broadcaster opt-in, conservative thresholds, a visible countdown, and an override, and it never labels the streamer as sleeping or eating
- Scheduled repeated studios during long unattended streams
- Cross-channel design-library browsing

Outside the feature entirely (section 5.3): unrestricted 3D modelling, uploading viewer camera streams to Ripple, server-side video analysis, diagnosing sleep, fatigue, or other personal states, arbitrary SVG or HTML uploads, survival power bought with paid events, and automatic changes to the Twitch broadcast or raid destination. The PRD's later features (L01-L09, PRD section 24) also remain unscheduled.

## Working rules

- Every feature is implemented as specified in the PRD and the addendum; no placeholder implementations.
- Each phase is delivered as a series of focused commits pushed to the main repository.
- The README is updated as capabilities land, describing only what actually works.
- Cocoon Studio stays optional: normal gameplay keeps working without cameras or studio participation, and camera and gesture code never enters the engine (addendum sections 2 and 25).
- The deployment stays one TypeScript application service plus PostgreSQL; the studio adds no vision backend, GPU server, video relay, or extra database (addendum sections 4, 15, and 26).
